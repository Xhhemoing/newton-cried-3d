# 兴趣卡性能优化

在开发时提前遵循性能规范，用户主动提出性能问题时检查并在请求授权范围内修复；保持原有业务、展示、接口与服务域。具体优化规则由独立 reference 维护，不凭用户描述直接确定原因。

## 路径与入口

- 解析本文件绝对路径，将所在目录记为 `PERFORMANCE_SKILL_DIR`。本 Skill 内的 reference 均从该目录解析，不覆盖生产 Skill 的 `SKILL_DIR`。
- 沿用生产 Skill 或用户确认的目标工程，读取实际 `package.json`、工作区和构建配置，定位项目根目录 `APP_ROOT`、卡工程、实际产物目录和已有验证入口。兼容独立卡工程与宿主内的 `opencard/`；不因默认路径不存在重新初始化、迁移或升级工程。
- 首先读取 [优化项索引](references/README.md) 和 [开发者表达原则](references/creator-language.md)。读取过且仍可用的规则可以复用，缺失或有更新时补读。

## 开发与检查

- **开发阶段**：先读取索引和开发者表达原则，允许先探查工程、澄清需求和制定方案。在开始实现某项功能前，根据当时已明确的实现内容匹配索引，读取对应 reference 的完整内容；新增或改变实现方式时重新匹配并按需补读，不要求提前确定全部适用项，也不因应用单项规则单独执行 `pnpm verify`。
- **开发收尾复核**：本轮涉及兴趣卡代码、资源或配置时，全部代码完成后、完整项目验证前，读取 [检查与复验](references/verification.md) 的「开发收尾复核」，遍历索引并根据实际实现补查适用规则；首次开发检查本次生成的完整兴趣卡，后续迭代检查本轮改动及其直接影响范围。仅加载入口、只读开发时选中的条目或项目验证通过，都不能代替复核。
- **性能检查与修复**：用户主动询问性能问题或要求检查、优化时，先确认检查对象与已有证据，再读取 [检查与复验](references/verification.md)，遍历完整索引，按各条目的“检查时适用条件”逐项判断；符合条件或无法明确排除时，读取对应 reference 并继续核查。不能只检查开发时读取过或命令报错的项目。仅咨询或检查时给出结论与建议，不修改代码、不上传资源；请求包含优化或修复时，在授权范围内完成修复并验证，不把建议表述为已执行。

**性能变更须先获用户确认**：对已有工程实施性能优化的代码变更前，先完成只读诊断和影响分析，按 [开发者表达原则](references/creator-language.md) 向用户说明具体变更动作，并提示“本次调整可能涉及原有功能，建议重点确认……”后列出相关具体的功能或操作。获得用户对该具体方案的明确确认后才能修改；一般性的优化请求不替代这一步。未确认时停在方案阶段，不先改后问。已有确认覆盖当前方案时继续执行，不重复询问；新增或扩大变更范围时补充确认。仅检查、未发现可实施方案，或正常开发新功能时遵循性能规范，不因此增加确认。

读取规则不等于完成检查。当前代码的项目验证通过、性能规则符合要求和实际体验改善是不同结论。缺少规则、工具或证据时，按 [检查与复验](references/verification.md) 补查；仍无法继续则停止该项操作、保留原实现并继续其他独立项，不伪造结果、不自动发布。

**涉及原功能的修改前后必须确认影响**：删除、延后或合并启动工作，改变注入数据、请求、刷新或状态提交时，先按 [业务影响确认](references/verification.md) 明确原行为、拟改变的顺序、受影响功能及保持原行为的证据，再实施修改；修改后按实际 diff 逐项复核。不能用“首屏不使用”“已有预取”或完整项目验证通过替代功能判断。关键影响无法确认时保留该项原实现，不把验证责任交给用户兜底。
