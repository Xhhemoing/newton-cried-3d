# Microapp Debug Pipeline

## 定位

业务 debug 只分 **UI** 和 **功能**。将用户反馈或审核打回转成可核验的具体问题，再到当前沙盒确认根因、最小修复和原路径复验。预览启动和发布代码错误保留专用路由，不要求 UI/功能问题先出现发布失败。只修已复现的问题，不重做产品，不替代生成 Skill 或全量质检。

先解析本文件的绝对路径，所在目录记为 `SKILL_DIR`。本 Skill 内资源一律使用绝对路径。

UI/功能问题涉及浏览器时，直接读取同级 `${SKILL_DIR}/../interest-card-browser/SKILL.md`，其绝对目录记为 `BROWSER_SKILL_DIR`。预览准备、Feed、点击/输入/滚动、请求、状态观测、截图和浏览器收口统一使用内置 `interest-card-browser` Skill，脚本用 `${BROWSER_SKILL_DIR}/scripts/...`；本 Skill 只负责问题分流、根因定位、最小修复和原路径业务复验。

浏览器 Skill 或所需脚本不可用时，浏览器验证记 blocked；可继续只读代码定位，不临时补装、复制旧脚本或另写一套浏览器工具。

UI 验收需实际查看截图像素；仅能保存 PNG、读取 DOM 或 OCR 时，视觉复验保持 blocked，可继续代码定位与不依赖目检的功能检查。

## 验证边界

- 按正常 QA 流程操作当前沙盒：可以点击、输入、提交、刷新、重试，可以用 `curl` 调用本地接口，可以产生和清理本轮本地测试数据。沙盒本地数据与线上数据隔离，不因写入本地成绩、记录或昵称而跳过验证。
- 只对当前沙盒的 `127.0.0.1`、`localhost` 或已确认本地服务地址执行写请求。线上接口、支付、外部消息、真实个人信息、共享环境配置和不可逆操作不自动执行。
- 隐私协议和域名白名单是平台配置，不是沙盒本地数据。检查可读；补配前确认当前应用身份、配置归属及用户对具体配置变更的授权，按 [platform-config.md](references/platform-config.md) 增量处理，不因“修复 bug”就覆盖共享配置。
- 用户只要求检查时不改项目源码。UI/功能问题要先复现，再按原路径复验。
- 用户明确要求只读时，不重启服务、不安装或升级工具、不准备或清理测试数据，不执行会写库、保存记录、支付或外部发送的操作。只读接口、现有日志、源码和已打开页面可检查；无法无写入复现的路径记 blocked，不把未操作写成已验证。
- 平台开通失败或持续连库 `ETIMEDOUT` 属于预览问题，不得通过代码绕过。

## 分流

先区分审核标签、实际现象和待核实原因；审核意见是检查线索，不是已确认根因，也不代表整类问题都可自动修复。一次反馈有多个问题时逐项分流，不按标签批量改代码，不强制查询审核历史。

| 反馈性质 | 处理方式 |
| --- | --- |
| 已有实现的 UI / 功能缺陷 | 走下面的 UI / 功能流程，现场核实后最小修复 |
| 纯展示、长按依赖、卡面任务拆分、主题或权益不符 | 先对照用户已确认需求与设计；局部实现偏离可修，需要新增核心功能、重设玩法、重新分配卡页职责或改变权益门槛时，交付具体缺口、调整方案和验收条件，转设计/生成 Skill，不在 Debug 中另造玩法 |
| 命名不明确、名称泛化 | 按现有命名规范给建议；用户明确要求改名时转生成/元数据流程，不走完整浏览器 Debug，不自动写线上元数据 |
| 禁入服务、交易、留资、第三方引流 | 核对具体入口、内容与适用规则，给调整方案并先取得确认；不擅自删核心业务、改名包装或执行交易/留资验证，不承诺修改后一定过审 |
| 预览不可用或明确发布报错 | 走对应专用路由，不混成业务缺陷 |

设计/生成 Skill 不可用或需求、规则不明确时，交付待确认项与验收条件，保持未解决；给出方案不算已修复。

### 1. UI / 功能问题

按现象只读对应参考，执行顺序统一读 [debug-workflow.md](references/debug-workflow.md)：

- **UI**：空白、裁切、错位、导航不可读、图片与素材异常，读 [ui-issues.md](references/ui-issues.md)。
- **功能**：点击、输入、播放/生成、结果、保存、跳转与卡页状态异常，读 [functional-issues.md](references/functional-issues.md)。

涉及 TT API 的授权、保存、定位、媒体或网络能力时，在功能流程中按需读取 [platform-config.md](references/platform-config.md)，核对相关应用身份、隐私声明、域名类型与能力开通，不限真机报错或已发生失败，不另造业务分类。

不默认通读两份问题参考。UI 证据指向接口或状态错误时再转读功能参考；功能数据正确但显示异常时再转读 UI 参考。混合问题分别验收，只补受改动影响的路径，不展开全类测试。

有截图时先写出 `截图区域/现象 → 候选文件/组件/选择器 → 待核实原因`；有视频时先提取前置状态、动作和失败时刻，再映射代码。具体输入处理和兴趣卡/落地页识别见 `debug-workflow.md`。截图、视频和标签不能单独证明根因；当前页面不一致时记录差异再判断。

### 2. 预览问题

预览打不开、一直加载、`pnpm dev` 失败、`run_failed`、资源开通失败、持续 `connect ETIMEDOUT`。只读 [runtime-errors.md](references/runtime-errors.md)。可修的启动错误用全量 `pnpm verify`，并确认预览离开加载失败。不要读 `code-issues.md`，不要按产品缺陷截图。

### 3. 发布失败

用户消息是发布或部署失败。再分成下面两类，只走一类。

**代码工程问题**：原文命中 [code-issues.md](references/code-issues.md) 的签名（编译、包体积、PageIndex、SQL、缺依赖、Docker COPY 等）。只读该文件。按其中的新旧项目入口完成表内复检和静态 verify，退出码为 0 才停手；新项目不运行会自动启动服务的全量 `pnpm verify`。不要读 `runtime-errors.md`，不要做页面复验。交付只写根因、改动文件、表内结果和静态 verify 结果。

**UI / 功能问题**：平台反馈的是可见页面或业务行为问题时，回到 UI / 功能流程，不按发布签名猜改。

## UI / 功能闭环

按 `分析输入 → 映射代码 → 现场复现与核实 → 最小修复 → 原路径及受影响分支复验 → 交付` 执行。UI 与功能的检查、修改和复验操作分别在 `ui-issues.md`、`functional-issues.md` 维护；共用执行顺序、卡页首读与交付要求在 `debug-workflow.md` 维护。

交付逐项说明反馈现象、当前是否复现、根因文件/位置、改动、before/after 与真实业务结果。明确区分已修复、未复现、验证 blocked 和待产品/规则确认；转交或给出方案不算修复成功。不把本地修复、build 或 verify 通过写成线上已修复或审核已通过。

## 成功标准

- UI/功能问题：原失败路径有修复后的真实业务结果；UI 有新 PNG 目检，功能有真实操作与结果，状态问题有卡页两端结果。lint、verify 或 build 不能代替这次复验。
- 真机专属能力：浏览器只能验证入口、交互态和预览提示；授权成功、实际保存到相册或原生跳转未经真机原路径复验时保持 blocked。配置已补配不等于原失败已恢复。
- 预览问题：可修错误按 [runtime-errors.md](references/runtime-errors.md) 复验，预览从原入口可用。平台错误按错误码回复并保持 blocked，不把已回复或已转交写成预览恢复。
- 代码工程问题：复检表那一行和静态 verify 都通过。本地通过后请用户重新发布，不宣称平台侧已经成功。
- 只检查时不改项目源码。无法复现或验证的部分明确标记 blocked。

## 边界

- 不重做产品需求，不整体重画兴趣卡，不用删除核心功能、固定结果或额外跳转掩盖问题。
- 不替代生成 Skill 实现全新页面或接口，不自动提交、部署或发布。
- 不执行线上写入、支付、外部发送、真实个人信息提交或共享环境配置修改。
- 发布失败对不上 `code-issues.md`、没有文件和行、或同一命令修完仍是原错误时停手，询问用户或引导右上角 Oncall，不要猜改。
