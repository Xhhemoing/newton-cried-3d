# 检查、修改与原路径复验

本文件只服务 UI 与功能问题。预览问题和代码工程问题不要按这里截图或重走页面。

## 1. 分析截图并定位候选代码

先从用户反馈、截图或视频中确定具体异常，整理为 `目标页面/区域 → 前置状态 → 用户动作 → 预期 → 实际现象`；审核标签只用于选择检查项，不把“虚假交互”“结果不客观”等直接写成代码根因。仅有笼统标签时，先从当前核心路径核实；缺少关键前置或预期时做最小澄清，不强制获取历史轨迹。

- **截图**：先目检具体区域、可见异常与预期，区分宿主与业务组件；截图不能证明按钮点过、请求完成或结果已保存。
- **视频**：使用已有视频查看能力提取 `时间点 → 前置状态 → 用户动作 → 可见反馈/失败时刻`，必要时查看动作前、失败时刻和结束态的关键帧，再定位对应控件与代码。单帧不能替代动作时序；视频无法查看时记录缺失，可按已知步骤现场复现，不猜视频内容。
- **无可查看素材**：先捕获当前原路径问题态，再映射代码；反馈与现场不一致时说明差异，未复现不猜改。

先确定兴趣卡还是落地页：用户明确点名 → 截图/视频可识别的 Feed 外壳或小程序导航 → 只读搜索文案在 `opencard/src/` 或 `src/pages/` 的归属；仍不明确时先询问，确认前不改文件。兴趣卡核对固定业务容器，落地页按实际滚动页面检查，不把卡面无滚动约束套用到落地页。

定位代码前，读取项目已有的 `AGENTS.md` 并遵循相关约定。用可见文案、控件或资源字段搜索对应页面，读取组件、直接样式和数据来源，记录 `截图区域 → 文件/组件/选择器 → 待核实原因`。宿主标题、按钮、icon/封面问题优先核对 `feed/feed-card.json` 或实际元数据来源，不默认都是业务组件 CSS。

重复报障先核对上一轮补丁、当前源码与实际运行/扫码产物是否一致，不把旧最终回复当恢复证据。涉及 TT API 的授权、保存、定位、媒体或网络能力时，按需走 [platform-config.md](platform-config.md) 核对适用配置，不限真机问题。

按需读需求/设计、`feed/feed-card.json` 与注册路由，固定当前入口、实际业务尺寸、前置状态、用户动作、预期和实际结果。不先遍历整个工程，不先跑全量 verify；只检查时不改源码。

## 2. 现场核实与浏览器复现

使用 `interest-card-browser` Skill 完成 readiness、真实 Feed 初始化、页面动作、被动请求观察、截图和收口。读取 `${SKILL_DIR}/../interest-card-browser/SKILL.md`，其目录记为 `BROWSER_SKILL_DIR`；需要命令细节时只读该 Skill 的 `references/operations.md`，不维护另一套浏览器操作流程。

直接使用内置浏览器 Skill，按实际安装的工具版本操作。严格只读任务不执行其安装/升级或服务启动步骤；先核对目标动作是否会保存记录、写库或发送外部请求，有写入副作用的动作不执行并记 blocked。缺少截图查看能力只阻塞视觉验收，不把 OCR/尺寸替代目检。不要重复读取帮助或创建临时浏览器探针。

UI 核对异常组件的实际 rect、父级高度/宽度链、裁切和资源解码；功能核对 `handler → 状态 → 请求/计算 → 渲染/保存`。用现场证据确认候选代码如何导致异常，再修改；截图与当前状态不一致时记录差异，不对旧截图猜改。根因明确后停止扩大搜索。

只观测问题选择器及直接祖先，使用浏览器 Skill 的 `inspect-preview-state --selectors-json`，不临时编写另一套 CDP。readiness 成功但 frame 空白时先读 `diagnostics.scriptFailures/hostNeedsData`；具体脚本 4xx/5xx 优先核实该资源，Feed 初始化丢失按既有 inject 流程恢复，有证据后最多重试一次。

证据写入本轮 `WORK_ROOT`，不写进项目源码。保留操作前、错误态及实际修改后的同态 PNG、真实 URL/路由、可见正文与请求回执；没有修改时不命名 after-fixed。图片须实际目检，CLI、ready 或 PNG 存在不证明业务通过。Feed 不可用时继续可独立打开的落地页检查，CTA/首读仍记 blocked。

非严格只读任务按正常 QA 流程验证当前沙盒，允许真实页面产生本地成绩和记录；确需接口准备或清理本轮本地数据时按本 Skill 验证边界执行，记录实际输入与返回。不伪造身份，不用接口调用、DOM 修改或手调 handler 代替浏览器失败路径。

## 3. 卡页状态检查（按需）

存在状态问题时，先冻结卡侧本轮结束结果、动作/请求、正文、时间和 PNG，再按 `interest-card-browser` 的 CTA 流程打开落地页。桥接信号仅证明宿主接受动作，跳转与状态承接独立判断。

在任何落地页同类写入前保存首个稳定值，使用浏览器 Skill 的 `preview-session observe` 留下原始 `values/observedAt/evidence`。按实际语义区分本轮结果、历史最佳和累计次数；确认 same/mapped 关系后对账，明确独立则记录依据。未捕获首读记 blocked，不用后续落地操作补造首读，也不修改回执凑 passed。

## 4. 最小修复与原路径复验

仅在用户要求修复时执行。沿错误结果定位最少文件，先修 handler、状态、布局或路由等真实根因。涉及卡页语义时两端同步，不整包覆盖模板或顺带重构。保留修复前截图便于同路径对比。

按每类的“检查操作”先固定一个 Case：`前置状态 → 用户动作 → 预期 → 实际错误 → 根因位置 → 最小改动 → 同路径实际结果`。同一问题可关联其他类别，但不因此扩大到全类重测。修复前未复现错误或仅为产品/合规建议，不能包装成已验证技术修复。

复验必须包含：

- 原 Case 同一前置状态、入口、控件、操作和预期；修复后真实结果与新 PNG 目检。
- 相邻一条正常路径，以及受改动影响的空态/重复操作/返回/重新进入分支；只测适用项。
- 卡页改动时检查落地首读；视觉改动时检查相关视口、长文案/长列表及 CTA 可见性。
- 先核对修后实际样式/数据已更新，再保存 after PNG；仍是旧值时先处理构建更新和 Feed 初始化，不用旧截图或改文件名凑验收。
- 最窄已有测试/lint，然后项目已有 verify/build；不得吞退出码，`cmd | tail` 不可拿 tail 的 0 当原命令通过。正常修复需要运行项目已有校验；用户明确只检查时不改源码，任何模式都不修改启动流程脚本绕过失败。

交付时按 Case 说明：`UI或功能/反馈与素材时间点/当前是否复现/前置与操作/预期/实际/根因文件与位置/最小改动/before与after/原路径结果/相邻复验/状态/未覆盖项`。UI 必须逐项目检截图，功能必须同时核对可见反馈与业务结果。状态用 `passed/failed/blocked/skipped`，跳转和 stateHandoff 独立判断。只有本轮确实修改并完成复验时才写“已修复”；未复现不是历史反馈不成立，转交方案或本地修复不代表审核已通过。

最终关闭本轮 session，不动其他页面或进程。交付问题结论、改动与验证范围，不自动上传、发布或提交。

涉及平台配置时单列目标归属、已核对项、实际增量变更和读回结果；原生授权/保存/跳转未经真机验证时直接列 blocked，不等用户追问才补充边界。不能用“所有问题已修复/浏览器全部通过”概括仍受阻的原失败路径。

## 专用测试沙盒构造 Case

仅当用户明确要求构造缺陷时使用，不属于正常验证。先记录 baseline hash、已有工作区差异和项目身份，备份受影响文件到 WORK_ROOT；每次只构造一个可回退源码缺陷，等实际构建更新后重新加载。保留原需求/预期，不用修改 DOM、假数据或改预期让结果通过。

执行“基线 → 缺陷 → 检测失败 → 定位补丁 → 原路径复验 → 相邻正常分支”，失败和修后各保存实际观察/PNG。当前沙盒本地测试数据可正常读写和清理；支付、外部发送、线上数据和共享配置仍不执行。结束恢复本轮所有临时源码改动，核对 baseline hash 与原工作区状态；保留测试结果，不提交/发布。

样本只证明该具体缺陷的检测与恢复有效，不证明整类所有项目可自动修复；视觉未目检、原生能力未实测、准入规则未确认必须单列未覆盖。
